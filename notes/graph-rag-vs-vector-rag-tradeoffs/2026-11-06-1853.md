## TIL: Graph RAG vs. Vector RAG Tradeoffs

**Vector RAG** excels at semantic similarity search ("find chunks like this query"). It is fast, cheap to index, and ideal for unstructured "needle-in-haystack" fact retrieval. However, it struggles with multi-hop reasoning, entity resolution, and global summarization because it lacks explicit structural relationships between chunks.

**Graph RAG** constructs a knowledge graph (entities + relationships) from source text, enabling structured traversal. It dominates at complex queries requiring connection synthesis ("How does A influence B via C?"), global overviews, and reducing hallucination via grounded paths. The tradeoff: significantly higher ingestion latency/cost (LLM-based entity extraction), schema rigidity, and complex retrieval logic (Cypher/Gremlin vs. ANN search).

**Hybrid approach** is usually optimal: Vector search for candidate retrieval + Graph traversal for context expansion and verification.

```python
# Conceptual Hybrid Retrieval (pseudo-code)
def hybrid_retrieve(query, vector_store, graph_db, k=5):
    # 1. Fast semantic candidate selection
    vectors = vector_store.similarity_search(query, k=k*2)
    entity_ids = {chunk.metadata['entity_id'] for chunk in vectors}

    # 2. Graph expansion: 1-hop neighbors for context
    context_entities = set()
    for eid in entity_ids:
        neighbors = graph_db.run(
            "MATCH (n {id:$id})--(m) RETURN m.id LIMIT 10", id=eid
        )
        context_entities.update(n['m.id'] for n in neighbors)

    # 3. Fetch full chunks for expanded entity set
    return vector_store.get_by_ids(list(context_entities)[:k])
```
